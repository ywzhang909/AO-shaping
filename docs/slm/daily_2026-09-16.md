## 1. 崩溃事实: n=5 实机 3/3 崩溃 0xC0000374

| 尝试 | 命令参数 | 崩溃迭代点 | 崩溃码 |
|---|---|---|---|
| attempt1 (11:40) | `--n-max 5 --magnitude 3.0 ...` | **18/20** | 0xc0000374 |
| attempt2 (11:45) | 同上 | **7/20** | 0xc0000374 |
| attempt3 (11:57) | 同上 | **(13/20) (4,2)** | 0xc0000374 |

- `0xC0000374` = STATUS_HEAP_CORRUPTION, faulthandler 检测点在 `thorlab_wfs.py` L1493 (`get_zernike` 内下一次 `np.empty((coeff_num,), c_float)` 堆分配处)。
- 崩溃迭代点不同 (18/20, 7/20, 13/20) → **非确定性的概率性小幅越界** (写越边界 ≈ 数十字节量级)。
- 对照: 修复前 n=10 实机 **65/65 全成功** (无崩溃) — 修复不触碰原生路径, 回归可能性低但未排除。
- faulthandler 检测点 ≠ 越界源头; 源头必在**更早**的原生 DLL 调用, 因为堆块在被 malloc 时校验已损坏的相邻块头部。

## 3. 决定性实验: WFS-only 隔离探针 **PASS (80/80)**

按城市规划的二分法, 写 WFS-only 探针隔离 WFS DLL (`scripts/wfs_probe.py`), 不开 SLM, 循环镜像 runner `_capture_wfs_full_state` 调用序列:

```
wfs.take_image() → wfs.get_spot_deviation(cancel_tile=False)
→ wfs.get_zernike(zernike_order=10) → wfs.get_wavefront(cancel_tile=False)
```

- 80 次迭代 ≈ **4× n=5 全标定工作量** (n=5 = 2 符号 × 20 模式 × 2 次捕获 ≈ 40 次捕获; 探针 80 次, 且每 20 迭代强制 `gc.collect()` 制造堆块腾挪提高越界触发率)。
- 注: 运行前发现官方 WFS 软件 `wfs.exe` (12:11 启动) 占用设备 → 用户手动关闭后重跑。
- **结果: 80/80 全部 PASS, 0.03s/iter, 累积 5360 个 zernike 元素, 零崩溃。**

原始日志: `data/slm_corrections/wfs_probe.log` (pupil=(-0.230,0.123)mm d=(3.569,3.789)mm, z[0..5] 稳定读值)。

## 4. 结论: 嫌疑从 WFS DLL 转移至 **Santec SLM 写入路径**

```
WFS-only (80 iters, 无 SLM)   → PASS, 零腐蚀
n=5 全流程 (SLM+WFS, 40 捕获)  → 3/3 崩溃 0xC0000374
```

WFS DLL 单独运行 4× 工作量无腐蚀 → **WFS DLL 侧排除**。剩余唯一变量 = **SLM 写入**。当前唯一残留嫌疑:

> **4.6MB `dat` 缓冲生命周期**: `_write_to_memory` 分配 `(ctypes.c_ushort * (width*height))()` 传给 `SLM_Ctrl_WriteMI` 后, Python 侧即释放。若 Santec DLL 为**异步 DMA 写入** (fire-and-forget), 释放后堆块可被下一个 malloc 复用 → DLL 仍在写 → 堆损坏 (概率性, 与观察一致)。反证: 相位图案显示正确暗示同步拷贝, 但异步写入 + 图案最终落盘也不矛盾。**低成本保险修复 = 驱动留存最近 N 个 `dat` 缓冲。**
