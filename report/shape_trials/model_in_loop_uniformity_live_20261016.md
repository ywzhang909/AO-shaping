## 结论

在 `128×128` 模型网格、60 CCD 像素目标和默认 `CV/EE=0.4/0.6` 权重下，
从已验收相位热启动两轮，固定 **0.200 ms** 的 `flat,A,B,flat,B,A,flat`
交错重放中，目标框 CV 均值由 **0.5627 降到 0.4454**（下降 20.8%），
EE 均值由 **0.4251 升到 0.4438**。A 为初始相位，B 为两轮后相位；
两次 A 的 CV 为 0.5648、0.5607，两次 B 为 0.4429、0.4480。
平相位在固定 0.100 ms 下的原始峰值为 75、73、76/255，
本组对照未见足以解释 CV 差值的平相位阶跃。

这证明当前光路下继续使用 CCD 反馈可以改善已生成光斑的目标框 CV。
但最佳候选的运行中形状 IoU 仅 **0.1236**，保存的 CCD 图像仍有明显结构散斑，
**尚未生成均匀实心方斑**。重放时成形帧原始峰值仅 18–21/255，
短曝光低计数非线性和量化仍限制对小幅差异的解释。

### 上文那条分歧的根因在代码里

`scripts/slm/model_in_loop_hw_runbook.py` 第 870 行把

```python
aperture_m=sweep_radius * SLM_PITCH_M
```

传给 `calibrate_bench_geometry_from_sweep`。`sweep_radius` 是 **sweep 阶段用来
构造 Zernike 模式的半径**（默认 200 px），不是实测的照明口径。而两条焦面尺度
推断（ramp 路线 vs 视场比路线）都与 `aperture_m` 成正比，所以一个未经实测的
口径会同时污染两个估计 —— 这与上文记录的「相差 152%」和代码
`model_in_loop_shaping.py` 里那条「most likely the illuminated aperture
radius ... Re-measure it with `beam_extent`」的 warning 指向同一处。
**即：上文要求的「优先校准照明束腰」在代码里的落点就是这个参数。**

### 第二次集成实测：两个由实测数据揭出的实现缺陷

半径探测首次在实验系统上运行（2026-10-17 10:00–10:06）返回
`radius_px=450 / x 边 1200 / y 边 900`。逐项核对原始 profile 后，
这个 450 是错的，且错法正是本节开头警告过的那个假设：

**缺陷 A：半径用 `远边界 / 2`，等于假设光斑贴着面板原点。**
x 向 profile 实测为
`0.99 1.0 1.0 0.99 0.97 0.92 0.84 0.72 0.61 0.52 0.49 0.48 0.48 0.48 0.48 0.49`
（档位 120…1920）。响应在 600 px 前几乎不变、到 1320 px 才触底，
即光斑横跨约 **660–1290**，中心约 975、半径约 **315**。
`1290/2 = 645`、`900/2 = 450` 都建立在「照明从 0 开始」这个本实验系统
并不成立的假设上。正确算法是 **半径 = 远边界 − 已测中心**，中心取
`panel_locate`／侧栏入射中心（本次 `(960,720)`）。已改，并加了显式
「无中心就报错、绝不退回 edge/2」的分支与回归测试。
⚠️ 该工具自身的日志一直写着「if the beam is centred, that implies …」——
即它自己就把半径标成了**有条件的**估计。

**缺陷 B：曝光探测返回了一个「工作曝光」，但从不校验它是否截断。**
同一次运行日志为
`上限 0.2430 ms（最后未饱和 0.6400 ms），工作曝光 0.1215 ms，峰值 255/255 (100%)`。
阶梯给的上限是响应的**模型**，而确认帧恰好证明这个值是截断的；
首版照样把它当「可用工作曝光」返回并写进侧栏。已改为：重新武装后**必须**取
确认帧，峰值 ≥90% 满量程就按比例回退（目标 55%）重试，最多 3 次，
仍饱和则报错并提示降功率/加衰减。

**两条都是「工具给出自信结论、而原始数据不支持它」的形态**，
与本节开头那次相机未接入的假读数同类：护栏缺失时，噪声会被当成测量。

### 修复后重测（10:10–10:15）

同一命令、同一光路，修复后：`曝光上限 0.5164 ms → 工作曝光 0.1420 ms，
确认帧峰值 77/255 (30%)`。缺陷 B 的校验生效 —— 返回值不再是截断值
（修复前同一位置是 255/255）。远边界 `x 1320 / y 900`，
中心取 `(960,720)` 时 `radius_x 360 / radius_y 180`。

⚠️ **但 360×180 是 2:1 的椭圆，对一个经过球面透镜的高斯光斑不合理。**
成因已定位：`(960,720)` 是**上一次会话** `panel_locate` 的结果，不是本次实测。
把同一组远边界配上面板几何中心 `(960,600)`（面板 1920×1200）：

| 中心取值 | radius_x | radius_y | 长短轴比 |
|---|---|---|---|
| 上一会话 `(960,720)` | 360 | 180 | **2.00** |
| 面板几何中心 `(960,600)` | 360 | 300 | **1.20** |

1.20 是合理的光斑形状，2.00 不是。**结论：半径对中心极其敏感，
中心必须与半径同会话实测**（`radius = edge − centre`，两项都变）。
这与本节开头「不作为下次启动的固定参数」是同一条纪律，只是这次它
决定的是一个物理孔径，而不只是曝光。

因此 GUI 侧「探测半径」的实现是：优先取**本会话**的入射中心
（人工填的 > 探测值），取不到才用调用方传入的提示值。
本次为了让命令能独立跑完而传了上一会话的 `(960,720)`，
所以 180 px 这个数**不可作为口径使用**，只作为「实现已正确执行换算」的证据。

### 半径改为「扫描自身落差宽度」，摆脱对中心的依赖

上一节暴露的问题不是「中心测错了」，而是**半径本来就��该依赖中心**。
边界扫描的响应有一条完整形状：边界穿过光斑近边缘前保持 ≈1，穿过过程中下落，
越过远边缘后贴底。于是**落差的宽度就是该轴的光斑直径，落差中点就是该轴中心** ——
两者都来自同一次扫描，与 `panel_locate` 无关。

用同一批 2026-10-17 实测 profile 离线重算：

| 轴 | 远边界 | 落差区间 | 扫描半径（±1 档） | 扫描中心 | 减中心法（上一会话 / 几何中心） |
|---|---|---|---|---|---|
| x | 1320 | 600 – 1320 | **360 ± 120** | **960** | 360 / 360 |
| y | 900 | 450 – 900 | **225 ± 75** | **675** | 180 / 300 |

三点值得记：

1. **扫描独立给出的 x 中心正好是 960**，与 `panel_locate` 完全一致 ——
   两条互不依赖的路径互为交叉验证。
2. **y 轴消除了 180/300 的二义性**：中心无关的估计落在 225，正处于两者之间。
   也就是说那个 1.6:1 的「椭圆」有相当一部分来自中心假设，而非光斑本身。
3. **不确定度是 ±1 档**：x 档距 120 px，对 360 的半径就是 **±33%**；
   y 档距 75 px 对 225 是 **±33%**。**所以当前档距下这个数仍不足以当口径用** ——
   缺的是分辨率，不是估计量。加密档位（如 32 档 → x ±60 / y ±37）才能把
   不确定度压到与两条焦面尺度分歧（152%）相比可忽略。

因此「自动扫最优」在本实验系统上的答案是：**估计量已经最优（一次扫描同时给中心
与半径，且不依赖外部中心），剩下的是把档距加密**。GUI 现在同时展示三个数
（扫描半径 ± 档距 / 扫描中心 / 减中心法结果），三者的分歧直接可见，而不是
其中一个悄悄覆盖另一个。

### 整轮漂移判据用错了物理量（2026-10-17 10:59 实验拒绝）

GUI 自动标定在实验上报 `session flat drift 7.9% exceeds 5.0%` 并中止。
逐行核对 `panel_locate` 后确认：**这个判据量的是强度，而强度漂移早已被逐点归一化
抵消，真正会让定位失效的位移却完全没检查。**

- 每个网格点的读数是 `(before_flat, candidate, after_flat)` 三元组，
  `_paired_delta` 用 `(before+after)/2` 作参考再取相对变化 —— 即每次测量都
  **自带当刻平场基准**，整轮的功率变化在这一步已被除掉。
- 而 `session_drift` 比的是首个 `flat_before_energy` 与末个 `flat_after_energy`
  的**绝对能量**，6 分钟内的激光功率变化直接落进去。
- 本实验系统的功率漂移本就很大（同一会话实测平场峰值 63 → 77 → 79 → 90），
  所以 7.9% 触发的是**正常的光强变化**，不是失稳。

已改：**整轮判据改为平场质心位移**（`session_shift_px`，默认限 3.0 相机px），
强度比降级为报告项并在日志里说明为何不影响定位。新增
`--panel-scan-max-session-shift-px`（0 = 关闭）。

⚠️ 这**改写了一条既有测试断言**：`test_scan_reports_session_drift_and_rejects_unstable_run`
原本断言 110% 强度漂移必须被拒。该断言编码的正是这个缺陷，故改为「必须通过」，
并新增 `test_scan_rejects_a_beam_that_moved` 用纯平移场景覆盖新的强制判据。

### 位移阈值必须随光斑尺寸缩放（同日 11:33–11:39 再次误杀）

改成位移判据后立刻又拒了一次：`session beam shift 3.47 cam px exceeds 3.00 px`。
但这次光斑是 `FWHM 62.9 px`、`peak 18/255`——**又宽又暗**。逐点核对质心轨迹：

```
cx: 1364.4 1365.5 1364.8 1364.1 1366.0 … 1367.1 1365.6 1365.6   （围绕 1365 随机游走，span 4.58）
cy: 1024.6 1027.0 1030.6 1031.3 1032.1 1033.1 1033.8 | 1018.8 …  （第2行起始跳回 -15px，随后缓慢爬升）
```

cx 是随机游走、cy 含一次阶跃——都**不是单调位移**，是宽暗光斑上的质心噪声。
而扫描给出的答案 `best_center 960,980`（-0.352）比次优 `960,720`（-0.322）高 9%，
3.47 px 的位移解释不了这个差距。

**结论：绝对像素阈值不可能同时服务 13 px 与 63 px 的光斑。**
已改为「阈值随光斑放大」：

```
limit = max(max_session_shift_px, max_session_shift_fwhm × 平场 FWHM)
```

默认 `max_session_shift_fwhm = 0.5`，绝对像素值降级为**下限**（紧而亮的光斑仍按它判）。
本次 62.9 px → 限 31.5 px，3.47 px 通过；13 px 光斑 → 限 6.5 px，同一绝对位移即被拒。
`FWHM`、`limit` 与 `max_session_shift_fwhm` 都写进 `summary.json`，判据可事后复核。

#### 实现时踩的坑：测试把这个 bug 一起复刻了

首版读的是 `getattr(flat, "fwhm", None)`，而真实类型
`SpotMeasurement` 的字段名是 **`fwhm_px`** —— 于是 `getattr` 恒返回 `None`，
「按光斑缩放」那段**永远不会生效**，实验仍会按绝对 3 px 拒。

更值得记的是它没被测试抓住：测试里我手写
`SimpleNamespace(fwhm=...)`，**复刻了同一个错名**，所以绿着。
这与仓库里那条「单指标会骗人」同源——**手搓替身照抄了实现者的假设，就不再验证任何东西**。

已修，并补一条断言直接检查真实 dataclass 的字段名：

```
assert "fwhm_px" in {f.name for f in dataclasses.fields(SpotMeasurement)}
assert "fwhm" not in ...
```

即：替身可以假，但**字段契约必须对着真实类型验一次**。
